Lesson 0002 • Low-Level Filesystem Mechanics

ext4 Blocks, HTree Collisions & Directory Internals

Decoupling directory entry blocks from payload data blocks, and dissecting the two independent hashing layers.

Primary Recommended Reading

Dive into the Linux kernel source implementation of directory entry lookups and HTree B-tree index structures in fs/ext4/namei.c (ext4_dx_find_entry) and the Birthday Paradox probability model.

1. The Two Independent Hashing Layers

A common source of confusion when reading ADR 0001 is mixing up Application-level hashing and Filesystem kernel-level hashing. They are two entirely separate systems operating at different layers:

Layer 1. Application Layer (Storage Engine) 2. Kernel Filesystem Layer (Linux ext4)
What is being hashed? The user's S3 Object Key (e.g. "photos/vacation.png"). The Filename on disk (e.g. "e3b0c44298fc...b855").
Hash Algorithm SHA-256 (FIPS 180-4 / RFC 6234). Half-MD4 or TEA (Kernel internal).
Hash Width 256 bits ($2^{256} \approx 1.16 \times 10^{77}$ combinations). 32 bits ($2^{32} \approx 4.29 \times 10^9$ combinations).
Purpose Eliminate CWE-22 path traversal; uniformly distribute files across 65,536 directories. Quickly locate which block inside a large directory holds a requested filename.
Collision Risk Virtually zero ($5.8 \times 10^{-47}$ at 10B items/day for 1,000 years). High once a directory exceeds ~65,000 entries (Birthday Paradox).

2. Why Do 65,000+ Files Lead to ext4 Hash Collisions?

When a directory contains only a few files, ext4 scans the entries linearly. But when a directory grows beyond a single 4KB block, ext4 activates HTree (Hash Tree), a shallow B-tree indexing mechanism.

To keep the B-tree compact and fast inside CPU cache, the Linux kernel designers chose a 32-bit integer hash for filenames inside HTree.

The Birthday Paradox in Layman Terms

In a room of just 23 people, there is a 50% chance that two people share the exact same birthday (out of 365 days). You don't need 365 people to get a collision! The math depends on the number of pairs of people: with 23 people, there are $(23 \times 22) / 2 = 253$ possible pairings.

The mathematical rule is: collisions begin appearing around the square root of the total possible slots:

Collision Threshold ≈ √(232) = 216 = 65,536 files

So, even though a 32-bit hash has 4.29 billion total numbers, dumping 65,000+ filenames into a single directory creates a high statistical guarantee that two completely different filenames will produce the exact same 32-bit HTree hash!

What Does an ext4 Hash Collision Actually Mean?

When two filenames produce the same 32-bit HTree hash:

  1. Data is NOT lost or corrupted: ext4 does not overwrite files.
  2. HTree cannot pinpoint the file: The B-tree index only leads to a "bucket" of colliding entries.
  3. Performance Degrades into a Linear Scan: The kernel must chain adjacent 4KB leaf blocks together. When you ask to open or stat a file, the kernel cannot do an instant lookup; it is forced to do a slow linear scan across all chained leaf blocks, performing byte-by-byte string comparisons on the filenames.
  4. Insertion Latency Spikes: Adding new files requires splitting leaf blocks and updating the journal while holding directory locks, causing severe throughput drops.

3. "What If the File Size Is Above 4KB?"

Crucial Distinction: Directory Blocks vs. Data Blocks

A directory block does NOT contain the file's payload data!

Think of a directory as a Phonebook, and the file payload as a House:

  • The phonebook entry is a single line: "Name: e3b0c4... | Address: Inode #48291".
  • The size of the house (whether it is a 500-square-foot apartment or a 50,000-square-foot palace) has zero effect on how many lines fit on a page in the phonebook!

(72B) │ │ struct ext4_dir_entry_2 (Entry 2): Inode #102 ──> Name: c3d4... (72B) │ │ struct ext4_dir_entry_2 (Entry 3): Inode #103 ──> Name: e5f6... (72B) │ │ ... (10 MB payload) │ (4,096 B) │ │ (4,096 B) │ │ (4,096 B) │ │ (4,096 B) │ └──────────────┘ └──────────────┘ └──────────────┘ └──────────────┘

Notice what happens:

  • Whether an object payload is 10 bytes, 4 kilobytes, 100 megabytes, or 50 gigabytes, its directory entry inside the leaf folder is always exactly 72 bytes!
  • The 4KB directory block holds up to 56 directory entries regardless of payload size.
  • At 1,000,000 objects in a bucket, each of our 65,536 leaf directories contains an average of 15 directory entries.
  • All 15 entries consume only $15 \times 72 = 1,080\text{ bytes}$, leaving 3,004 bytes of empty room inside the leaf folder's single 4KB block.
  • When Linux needs to find your file, it reads just that single 4KB directory block from disk (or pulls it instantly from RAM via the Linux dentry cache), finds Inode #102, and immediately begins streaming the payload data blocks.
