Lesson 0001 • Core Storage Architecture

Storage Engine Layout & Linux ext4 Internals

Understanding POSIX filesystems, ext4 limits, cryptographic hash addressing, and MIME decoupling in ADR 0001.

Primary Recommended Reading

Before diving into future distributed storage layers, read the canonical source on ext4 directory indexing: Linux Kernel Documentation: ext4 Directory Indexing and the Git loose object format in gitrepository-layout(5).

1. What is a POSIX Filesystem?

POSIX (Portable Operating System Interface) is a family of IEEE standards defining how Unix-like operating systems (Linux, macOS, BSD) must behave. A POSIX filesystem specifies how files, directories, permissions, and system calls interact.

In a POSIX filesystem:

  • Everything is organized into a hierarchical tree starting at root (/).
  • Data files and directories are tracked by inodes (index nodes) that store file metadata (size, permissions, timestamps, block pointers).
  • Directories are special files containing lists of names pointing to inode numbers.
  • Standard system calls (open(), read(), write(), unlink(), rename()) govern all operations.
The S3 vs POSIX Impedance Mismatch

In Amazon S3, there is no real directory hierarchy. Keys are just arbitrary UTF-8 strings. S3 allows an object named photos and an object named photos/beach.png to exist simultaneously. But on a POSIX filesystem, a single path component cannot simultaneously be a regular file and a directory! Attempting to create a file where a directory exists triggers EISDIR, and vice versa triggers ENOTDIR. Furthermore, raw S3 keys can contain ../../ or null bytes (\0), creating lethal path traversal security vulnerabilities (CWE-22) if passed directly to POSIX system calls.

2. What is ext4?

ext4 (Fourth Extended Filesystem) is the standard, rock-solid default journaled filesystem used by modern Linux distributions (including Ubuntu, Debian, CentOS/RHEL, and Android). It divides physical disk storage into fixed-size chunks called blocks (almost universally 4,096 bytes / 4 KB).

When you create an ext4 filesystem:

  1. A fixed pool of inodes is allocated.
  2. Directory entries (represented by struct ext4_dir_entry_2) map human-readable names to inode numbers.
  3. Each entry has an 8-byte header plus the filename bytes, padded to 4-byte boundaries.

3. ext4 Limits & Directory Scaling in Layman Terms

The Layman Analogy: The Giant Cardboard Box vs. The 2-Tier Filing Cabinet

Imagine you have 1,000,000 papers to store. If you dump all 1,000,000 papers into one single giant cardboard box (a flat directory):

  • Every time you want to find a paper, you must dig through a massive pile. Even with an index, the index is so large it overflows your desk.
  • Hash Collisions: ext4 tries to help you by creating a short 32-bit index (called HTree). But with 65,000+ items, two different names inevitably get assigned the exact same index slot (the Birthday Paradox). When that happens, the system is forced to slow down and perform a slow manual search across chained leaf blocks.
  • The Box Never Shrinks: In ext4, when you delete papers from the giant box, the cardboard box never shrinks back down! If it expanded to 71 MB on disk, it stays 71 MB forever, wasting RAM cache every time someone looks inside, until you take the filesystem offline for repair.

Now imagine you organize with a 2-Tier Filing Cabinet:

  • Drawer 1 (Tier 1): 256 folders labeled 00 through ff.
  • Drawer 2 (Tier 2): Inside each folder, 256 subfolders labeled 00 through ff (65,536 total folders).
  • With 1,000,000 papers, each subfolder holds an average of only 15 papers!
  • Because 15 files easily fit inside a single 4KB block (which holds up to 56 files), the computer reads the folder in a single instant disk read ($O(1)$) with zero index splitting and zero hash collisions.

4. Hashed Key Addressing: Why Lowercase Hex SHA-256?

In ADR 0001, every object key is addressed as:

hash = hex_lower(SHA-256(key.getBytes(StandardCharsets.UTF_8)))

Why this exact combination?

  • Raw UTF-8 Bytes: Cryptographic hashing functions do not operate on abstract string characters; they operate on raw byte arrays. Using explicit UTF-8 ensures identical byte sequences across Java runtimes on Linux, Windows, or ARM servers.
  • SHA-256 Collision Resistance: With $2^{256}$ possible outputs, the mathematical chance of two keys having the same hash is $5.8 \times 10^{-47}$ even after storing 10 billion items a day for 1,000 years. It provides mathematically guaranteed uniqueness.
  • The Avalanche Effect: Changing a single letter (e.g. photo1.jpg vs photo2.jpg) flips 50% of the bits in the output hash. This guarantees a perfectly random and uniform distribution across the 65,536 leaf directories.
  • Hexadecimal Encoding: The raw SHA-256 digest is 32 binary bytes, which can contain null bytes, control characters, or slashes (/). Hexadecimal converts this into 64 clean, safe ASCII characters (0-9 and a-f).
  • Lowercase Strictness: Linux ext4 is case-sensitive (abc and ABC are distinct files), whereas macOS APFS and Windows NTFS are case-insensitive. Standardizing on lowercase prevents subtle cross-platform corruption and file-not-found bugs.
  • Total Immunity to CWE-22 (Path Traversal): A malicious key like ../../../../etc/shadow hashes into 64-character alphanumeric string. There are no dots, no slashes, and no null characters. It is physically impossible to escape the storage root.

5. What are MIME Types & Why Are They Decoupled?

MIME (Multipurpose Internet Mail Extensions) types, formally known as Media Types (RFC 2046 / RFC 6838), tell clients what kind of data an object represents (e.g., image/png, application/pdf, text/plain, video/mp4).

In traditional desktop filesystems, the operating system guesses the file type using the file extension (like .png or .pdf). But in an S3-compatible storage engine:

  1. Payloads on disk have NO extension: The disk file is named strictly by its 64-character hash: 
    /data/buckets/my-bucket/e3/b0/e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855
  2. The disk engine only cares about raw payload bytes: It streams bytes in and out without inspecting their format.
  3. MIME types live in the Metadata Store (Database): When an object is uploaded, its human-readable key (e.g., vacation.png), its MIME type (image/png), its size, and timestamps are recorded in the database.
  4. Serving the object: When a user requests GET /my-bucket/vacation.png, the service looks up the metadata in the database, sets the HTTP response header Content-Type: image/png, and streams the raw bytes directly off the disk.
